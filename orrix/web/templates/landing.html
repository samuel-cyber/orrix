Buyer text stops at the reader. Only validated facts and an explicit approval reach the executor, and every step lands in a hash-chained audit log.

The problem

Give an agent both buyer text and the tools to act, and a crafted message becomes an instruction. The failure is not the model reading a message; it is the same component reading it and acting on it.

One context window

Most agents pass a buyer's message straight into a tool-calling loop. The same tokens that describe a problem also authorise a refund.

Authority by accident

"I am PayPal support" is text, but inside a single agent it is indistinguishable from an instruction the operator meant.

No separating wall

A prompt is a request for behaviour. Orrix uses a boundary the code enforces, not a sentence the model is asked to respect.

How Orrix works

Five steps. The reader has no tools, the policy consults no model, and the executor is the only module that can write.

  1. 1

    Read

    Untrusted buyer text becomes one validated claim form: a claim type, a clamped amount and a bounded summary. Nothing else.

  2. 2

    Decide

    Plain code decides what is allowed, using only trusted PayPal facts. No model touches the decision.

  3. 3

    Approve

    A seller approves exactly one action on one dispute version. The approval is bound to a payload hash.

  4. 4

    Submit

    The executor is the only module that can write, and only the approved payload reaches PayPal. Idempotent by approval id.

  5. 5

    Record

    Every step appends to a hash-chained audit log, so tampering is visible, not silent.
